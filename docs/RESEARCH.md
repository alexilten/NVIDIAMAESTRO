# Round 00: research and foundation

## What MAESTRO is for

Exhibition teams design demo stations around NVIDIA hardware many times a year. Each time they rebuild the same knowledge: how big a DGX Spark is, which side its ports are on, what a rack weighs, how the counter from the last show was built. MAESTRO keeps that knowledge in one place with its sources, lets a designer assemble a station from it in minutes, and hands the result to Rhino with dimensions and identity intact.

Four workspaces, built in rounds:

| Workspace | Purpose | Round |
|---|---|---|
| Discover | Find a product or part, inspect it in 3D with cited specifications | 01 |
| Compose | Assemble a demo module from products, kit parts and project parts | 01 (basic), 03 |
| Import | Turn parts of earlier project models into reviewed library components | 01 |
| Exhibition | Lay modules out on a floor plan with circulation and services | 04 |

## Data standard

### Every value carries a status

| Status | Meaning | Rule |
|---|---|---|
| Verified | Read from manufacturer documentation or an approved project record | Must cite a source id; the test suite enforces it |
| Project-specific | From an approved project model or drawing | True for that build only |
| Estimated | Derived, measured from a secondary source, or a design input | Shown in amber with a note saying why |
| Placeholder | Not known | Value is `null`; nothing is drawn to a guessed size |

A combined status (for example the overall dimensions of a product) is the weakest of its parts. A product with placeholder dimensions has no geometry: Discover says so instead of drawing a box.

### Levels of detail

| LOD | Name | Content |
|---|---|---|
| 0 | Envelope | Accurate overall dimensions as a clean volume |
| 1 | Proxy | Recognisable shape, principal materials and connection faces, generated from the recorded dimensions |
| 2 | Presentation | Exterior geometry good enough for client presentation; imported project parts are LOD 2 |
| 3 | Detailed | Manufacturer-informed geometry |

All Round 01 hardware geometry is LOD 1 procedural proxy, generated by MAESTRO inside the recorded envelope, and labelled as not manufacturer geometry. The tests check that every proxy is exactly its envelope.

### Schema

- **ProductFamily** groups models (DGX desktop, NVL rack-scale, Jetson…).
- **ProductModel** is what NVIDIA or a partner names: kind (system, rack, board, devkit, reference architecture, software platform), description, technical specs, applications, related models, and for reference architectures the physical racks that **implement** them.
- **PhysicalAsset** is the object that occupies space: dimensions, weight, rack units, interfaces by side, clearances, and its digital assets (each with LOD, provenance and version).
- **ParametricKitPart** is MAESTRO's own furniture: parameters with ranges and units, and a shape generator.
- **IngestedPart** is a reviewed component from a project model: source identity, exact source geometry, a display mesh, measurements, linked pages, dimension checks, status and version.
- **Composition** places any of these by reference (`product`, `kit` with parameters, or `ingested` with a version), with position, rotation, group and a snapshot of the dimensions used.

Modelling a reference architecture separately from the racks that implement it matters: "GB200 NVL72" is not one enclosure, so it has no dimensions; the GIGABYTE AI-DLC rack does.

### Conventions

Millimetres, Z up, item front facing −Y, origin at the centre of the footprint on the floor (imported parts keep their source origin, which is recorded). The Rhino export uses the same frame, so instances open in Rhino where they were placed.

## Audit of Stagework and ManicAI

Both are Alex's earlier generative design tools with the same shape: a Vite + React + R3F single-page app, glass panels over a full-screen 3D view, native Rhino export through rhino3dm, vitest, and GitHub Pages deployment.

| Reused | How |
|---|---|
| Stack and build | Same versions of React, Vite, R3F, drei, three, zustand, rhino3dm; same `tsconfig`, Pages workflow and build stamping |
| Interface language | Glass panels, toolbar, segmented controls, chips, view bar and toast, restyled with a green accent |
| Rhino export approach | Layer tree under one root, blocks for repeated items, user strings for identity, reopening the file to check it |
| Test habits | Round-trip tests on generated files, an independent Python check of exported `.3dm` files |

Not reused: the stadium and staging domain code. Neither repository was modified.

## Assessment of the first client project

The first project model is large (tens of thousands of objects, many blocks, authored partly in feet and with some blocks scaled or authored upside down). A cleaned kit master derived from it records, in each block description, which original block it copies. MAESTRO imports from that kit master, keeps the "derived from" link, and verified that a kit block matches the original part for part. Project files and anything derived from them are kept out of this repository (see the README).
